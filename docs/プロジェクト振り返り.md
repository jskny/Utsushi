# プロジェクト振り返り(レトロスペクティブ)

対象読者: Utsushi の保守担当者・このリポジトリで作業するAIエージェント。
関連: `docs/実装設計失敗事例集.md`(個々の不具合・設計ミスの記録)、`docs/開発環境メモ.md`(環境固有の注意点)

本書は、ひとまとまりの対応(プロジェクトのフェーズ)が終わるたびに、PMBOK の「教訓(lessons learned)」として
良かった点・悪かった点・改善の処置を記録する。個々の不具合の原因と対策は失敗事例集に書き、本書には進め方
(計画・品質・リスク・コミュニケーション)の振り返りを書く。新しい振り返りは先頭に追加する。

## 2026年11月: 入口の `Excel2Pdf` への一本化と診断の強化

### 概要

| 項目 | 内容 |
|---|---|
| 目的 | 実際に使われている `Excel2Pdf`(帳票定義なし)だけを残して保守の負担を減らし、表示が崩れる原因を開発者がすぐに分かるようにする |
| 仕様 | `.kiro/specs/excel2pdf-consolidation/`(要件1〜7、タスク1〜9・約70のサブタスク)、中核仕様の要件11.7(タスク31) |
| 成果 | 帳票定義・置換キー・`ReportPdfConverter` の削除、未対応要素の一覧と既定のエラー化、診断 `Check()`(フォントの代替・書式の近似を含む)、CLI の `check`/`convert`、代替フォント名の検証 |
| 規模 | PR #27(161ファイル、+9,082/−6,125行、53コミット)、PR #28(12ファイル) |
| 品質 | テスト約1,700件(すべて成功)、`dotnet format`・VS2019 のコンパイラでのビルドも成功。サブエージェントのレビュー(code・layout-fidelity・security・doc・spec-compliance)を各タスクの完了時に実施 |

### 良かった点(続ける)

1. **要件を詰めてから実装した。** 利用者との対話で、既定をエラーにする・書式の近似はエラーにしない・`clip` は不要・旧仕様を残さない、
   などを実装前に決めた。実装中に方針が揺れることがなかった。
2. **実装前の実現可能性の調査を設計に残した。** 調査の結論(design.md 9章)を先に書いたため、タスク8の削除の順序
   (Substitution → Layout → ReportDefinition)や移行期間の扱いで詰まらなかった。
3. **タスクを細かく分けた。** 1サブタスク=1コミットの粒度にしたため、レビューの単位が小さく、ワーカーの再起動・
   サブエージェントのレート制限で作業が中断しても、失ったものが無かった。
4. **ゴールデンの差分を事前に予測した。** design.md 6.1 に「差分はこの2種類だけ」と書いてから移行したため、
   layout-fidelity-reviewer が差分の妥当性を短時間で確かめられた(実際の差分は予測の範囲内だった)。
5. **レビューの観点を分けた。** code・layout-fidelity・security・doc・spec-compliance をそれぞれ別のサブエージェントで行い、
   互いに見落とすものを拾えた(例: security-reviewer は実測で、リッチテキストの読み取りが 183秒かかる計算量の問題を見つけた)。
6. **CI を待ってからマージした。** PR の購読で CI の結果を受け取り、緑を確かめてからマージした。

### 悪かった点(改める)

1. **同じ型の安全弁の漏れが、また後追いで見つかった。** 条件付き書式の範囲だけ一括の `Split` をやめたが、同じ型の
   `CellRange.TryParse`・印刷タイトル・図形の式は残り、次のレビューで見つかった(失敗事例集 4.5)。
   診断専用に読む型付きの値が不正な値でファイル全体を破損扱いにする問題も、2回に分けて見つかった(同 2.9)。
2. **移行中の注記と未来形の表現が、完了後も残った。** 「廃止予定」「〜するまで」「タスクNで改める」を多くの文書に書き、
   完了時の一掃が漏れた。spec-compliance-reviewer・doc-reviewer が十数か所を見つけた(同 6.4)。
3. **改名の後に古い名前が残った。** `ReportCode`→`DocumentName` などの機械的な改名の後、変数名・テスト名・コメントに
   `definition`・帳票定義が残り、レビューの nit が増えた。
4. **スカッシュマージ後のブランチの再利用で詰まった。** 環境メモの手順(`--force-with-lease`)が、自動の安全確認で拒否された。
   別名のブランチへの push で解決したが、利用者に判断を求める手間が生じた(同 6.5)。
5. **判断事項の伝え方が遅れた。** 「判断が必要な点」の一部(字形の無い文字のエラーの内容など)は、背景の説明が足りず、
   利用者から質問を受けてから具体例を示した。最初から具体例(どんな入力でどう出るか)を添えるべきだった。
6. **生成スクリプトの環境差に時間を取られた。** openpyxl の版で数式セルの書き出し方(`<v></v>`)が変わり、
   エッジケースのサンプルの生成が失敗した(環境メモ 10)。

### 見送ったこと(と理由)

- **hook の追加**: stop hook(未コミット・未 push の検出)は環境側で有効になっており、今回も機能した。`dotnet format` や
  テストを hook で強制する案は、ビルドに数分かかり対話を止めるため見送った。CI(`build-test`・`vs2019-toolchain`)が同じ確認を行っている。
- **スキルの追加**: spec 駆動の手順・レビューの手順は CLAUDE.md とサブエージェントの定義で足りており、繰り返し使う独立した
  手順(スキルにする価値のあるもの)は見当たらなかった。
- **サブエージェントの削除・統合**: 5種類のレビューはそれぞれ別の不具合を見つけており、統合すると観点が薄まるため残した。
