# 開発環境メモ(Claude Code on the web実行環境)

対象読者: このリポジトリで作業するAIエージェント(Claude Code)本人。ローカル開発機やCI環境には基本的に当てはまらない。

本メモの記載は、すべて2026年9月19日、Utsushiのセッション上で実際にコマンドを実行して確認した内容のみを採用している。他プロダクト(別リポジトリ)で作成された開発環境メモを出発点にしたが、そちらに書かれていてもこのセッションで裏取りできなかった項目、またはUtsushiの技術方針(`.kiro/steering/tech.md`)に該当しない項目(EF Core/MySQL関連など)は採用していない。実装作業中に環境起因の疑わしい挙動に遭遇したら、まず本書の該当節を確認し、新たに確認した事実があれば追記すること。

## 1. .NET SDK

- このセッションには `dotnet` コマンドはプリインストールされていない(`command not found`)。都度セットアップが必要。
- `apt-get update` 実行時、本プロジェクトと無関係な一部PPA(`ppa.launchpadcontent.net` 上の `deadsnakes/ppa`、`ondrej/php` 等)への `Invalid response from proxy: HTTP/1.1 403 Forbidden` エラーが混在するが、これは無視してよい。Ubuntu本体のアーカイブ(`archive.ubuntu.com` 等)の取得自体は成功しており、`apt-get install` の成否とは無関係。**apt-getのログにエラー文字列があるかどうかではなく、`dotnet --version`(または`command -v dotnet`)の終了コードで判断すること。**
- `apt-get install -y dotnet-sdk-10.0` は実際に成功し、`dotnet --version` は `10.0.112` を返した(このセッションでの実測値)。
- `apt-cache search dotnet-sdk` で確認したところ、このセッションのapt標準リポジトリ(Ubuntu 24.04 noble)には `dotnet-sdk-8.0` と `dotnet-sdk-10.0` のみが存在し、`dotnet-sdk-5.0`/`dotnet-sdk-6.0` は候補にない(Utsushiの技術方針である .NET 5 はEOLのためaptから外れている)。

### .NET 5 (net5.0) をこの環境でビルド・テストする方法(実機検証済み)

Utsushiは呼び出し元プロダクトが .NET 5 であるという制約上、`net5.0` をターゲットフレームワークから変更できない(`.kiro/steering/tech.md` 参照)。**.NET 5 のSDK/ランタイムを別途インストールする必要はなく、apt-getで入る `dotnet-sdk-10.0` だけで `net5.0` のビルド・`dotnet test` 実行まで一通り確認できた。** 手順と根拠は以下の通り(`/tmp` 配下のスクラッチプロジェクトで検証)。

1. **ビルド**: `<TargetFramework>net5.0</TargetFramework>` のクラスライブラリ/コンソールアプリは、.NET 10 SDKのままで `dotnet build` が普通に成功する。`net5.0` 用の参照アセンブリ(reference assemblies)はNuGetから自動的に復元されるため、SDK側に対応するランタイムが入っている必要はない。ビルド時に `warning NETSDK1138: The target framework 'net5.0' is out of support` という警告が出るが、これは想定通りで無視してよい。
2. **既定のC#言語バージョンに注意**: `net5.0` の既定 `LangVersion` はC# 9相当で、file-scoped namespace(`namespace Foo;` 構文)等C# 10以降の構文は使えず `CS8773` でビルドエラーになる。使いたい場合は `.csproj` に `<LangVersion>10.0</LangVersion>`(以上)を明示する。これは純粋にコンパイル時の言語機能の話であり、生成されるILは引き続き `net5.0` 互換のままなので、呼び出し元(.NET 5)プロダクトとの互換性には影響しない(実機確認済み)。
3. **実行(テスト含む)には `RollForward` が必要**: ビルドした `net5.0` アセンブリをこの環境でそのまま実行しようとすると、`Framework: 'Microsoft.NETCore.App', version '5.0.0' ... The following frameworks were found: 10.0.12` というエラーで起動に失敗する(.NET 5ランタイムが実機に存在しないため)。`.csproj` に `<RollForward>LatestMajor</RollForward>` を追加すると、生成される `*.runtimeconfig.json` に `"rollForward": "LatestMajor"` が書き込まれ、インストール済みの新しいランタイム(このセッションでは.NET 10.0.12)にロールフォワードして正常に実行できる。CLIから都度 `dotnet --roll-forward LatestMajor <dll>` を付ける方法や `DOTNET_ROLL_FORWARD=LatestMajor` 環境変数でも同様に効くが、`dotnet test` はこれらのCLIオプションを素直に通さないため、**`.csproj` 側に `RollForward` プロパティとして書いておく方法を標準にする**こと。
4. **`dotnet test` の動作確認**: `net5.0` + `<RollForward>LatestMajor</RollForward>` のxUnitテストプロジェクト(`Microsoft.NET.Test.Sdk` 17.1.0 / `xunit` 2.4.1 / `xunit.runner.visualstudio` 2.4.3 の組み合わせ)で `dotnet test` を実行し、実際に `Passed! - Failed: 0, Passed: 1` となることを確認した。より新しいパッケージバージョン(`Microsoft.NET.Test.Sdk` 17.11.1 / `xunit.runner.visualstudio` 2.8.2)の組み合わせでは「No test is available」となりテストが発見されなかった(net5.0とのパッケージ互換性の問題とみられる)ため、テストパッケージは net5.0世代のバージョンに合わせること。
5. まとめると、Utsushiの `.csproj` は最低限以下を含める。
   ```xml
   <TargetFramework>net5.0</TargetFramework>
   <LangVersion>10.0</LangVersion>
   <RollForward>LatestMajor</RollForward> <!-- 実行可能プロジェクト・テストプロジェクトのみ -->
   ```

## 2. 日本語フォント(PDF出力の動作確認に必要)

- **この環境には日本語フォントがプリインストールされていない**(初期状態の `fc-list` はDejaVu/FreeFont/Bitstream等の59件のみで、`fc-list :lang=ja` は該当なし)。
  自社帳票が使う `MS PGothic` 等は当然存在しないため、`FontResolver` の既定(厳格モード)では
  `FontNotAvailableException` になる。これは実装どおりの挙動であり、環境の不具合ではない。
- 日本語を含むPDFの見た目を実際に確認したい場合は、IPAフォント(IPA Font License、再配布可)を入れる。
  `apt-get install -y fonts-ipafont-gothic fonts-ipafont-mincho` が実際に成功し、
  `IPAGothic` / `IPAMincho` が `fc-list :lang=ja` で見えるようになることを確認済み。
- CLIで試すときは `--allow-font-fallback IPAGothic` を付ける。**見た目は実帳票と一致しない**ため、
  レイアウトの検証には使わないこと。レイアウトの回帰検出はゴールデンテスト
  (決定的な `ApproximateFontMetricsProvider` を使うためフォント非依存)が担当する。
- **太字の注意点**: IPAフォントには太字の字形が無く、SkiaSharp が字形を合成する(fake bold)。
  この場合 PDF には Type 3 フォントとして出力され、文字列検索ができずファイルサイズも増える。
  太字が多い帳票の確認では、太字の字形を持つフォントを使うこと。

### 生成したPDFの確認方法

`apt-get install -y poppler-utils` で入る以下のコマンドが使える(実際に動作確認済み)。

```bash
pdfinfo out.pdf                  # ページ数・ページサイズ・メタデータ
pdffonts out.pdf                 # 埋め込みフォントの種別(Type 3 か CID TrueType か)
pdftoppm -r 100 -png out.pdf page   # ページを画像化して目視確認する
```

- `playwright install` は実行しないこと(再ダウンロードが走る)。利用するPlaywrightパッケージのバージョンとプリインストール済みChromiumのバージョンがずれて起動に失敗する場合は、`playwright install` ではなく、上記のプリインストール済み実行ファイルパスを明示的に指定する(C#の場合は `Microsoft.Playwright` の起動オプションに `ExecutablePath` を渡す等)。
- Utsushi自体にはまだPlaywrightを使うUI/Webがないため、上記は今後E2E的な検証(生成PDFのビューア確認など)が必要になった場合の前提情報として記録する。

## 5. `pkill -f` / `pgrep -f` の自己マッチ問題(重要)

Bashツールに渡したコマンドは、実際には `/bin/bash -c "<渡したコマンド文字列全文>"` という形で実行される(`ps -eo pid,ppid,args` で当該プロセスの `args` に渡したスクリプト全文がそのまま現れることを実際に確認した)。

このため、**`pkill -f "<パターン>"` を直接Bashツールのコマンドとして書くと、そのパターン文字列がコマンド文中に存在すること自体によって、呼び出し元の `bash -c` プロセス自身にマッチしてしまう。** 対象プロセスが実在するかどうかに関係なく、このBashツール呼び出し自身がSIGTERMで即座に終了し、後続の行は一切実行されない。`|| true` を付けても防げない(マッチした瞬間にシェルごと終了するため、`|| true` の評価まで到達しない)。

実証結果:
- `pkill -f "definitely-nonexistent-process-zzz123"` だけを実行 → 対象プロセスは存在しないにもかかわらず即座に終了(exit code 144)。後続の `echo` も出力されなかった。
- 同じ内容に `2>/dev/null || true` を付けても結果は同じ(即死)。
- 一方、`pkill "<15文字以内のプロセス名>"`(`-f` なし、プロセスの実行名との完全一致検索)は自己マッチせず、対象が存在しない場合は通常通り `exit 1` を返すだけで、後続の行も問題なく実行された。

対策:
- Bashツールの呼び出しに `pkill -f "<パターン>"` を直接書かない。
- 対象プロセスの実行名が15文字以内であれば、`-f` を使わない `pkill <プロセス名>` を使う(完全一致検索のため誤爆もしにくい)。
- 実行名だけでは対象を絞り込めず `-f` が必要な場合は、パターン文字列をリポジトリ内のスクリプトファイル(例: `scripts/dev/stop-dev-server.sh` のようなファイル)の内部に保持し、Bashツールからはそのスクリプトを短い引数で呼び出す形にする。こうすればBashツールに渡るコマンド文字列自体にはパターン文字列が含まれないため、自己マッチが起きない。

## 7. 確認したが採用しなかった項目(参考)

他プロダクトの開発環境メモに記載があり、このセッションで確認を試みたが、Utsushiには該当しない、または再現できなかったため本メモには含めなかった項目:

- **EF Core / MariaDB関連**: Utsushiの技術方針(`.kiro/steering/tech.md`)はデータベース(EF Core/MySQL)を前提としていないため、確認自体を行っていない。
- **`nohup dotnet run &` がこの環境で不安定になるという主張**: 単純な `nohup sleep 120 & disown` で試したところ、別のBashツール呼び出しをまたいでもプロセスは(PID 1へ正しく再親化された状態で)問題なく存続しており、この環境で一般的に不安定になるという主張は再現できなかった。ASP.NET Core固有の標準入出力の扱いに起因する可能性はあるが未確認のため、Utsushiで開発サーバーを常駐させる実装をした際に改めて検証すること。
- **コミット状況を確認するstop hook**: `~/.claude/stop-hook-git-check.sh` というスクリプトファイル自体はこの環境にも存在するが、本リポジトリのセッション設定(`.claude/settings.json` 等)に有効化する記載が見当たらず、実際に動作しているか確認できなかった。
- 別プロダクト固有のUIコンポーネント(Bootstrapモーダルのタブ切り替え等)やスクリプトパス(`scripts/dev/*.sh` 等)は、Utsushiには存在しないため対象外。
