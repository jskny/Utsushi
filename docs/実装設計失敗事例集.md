# 実装・設計 失敗事例集

対象読者: このリポジトリで作業するAIエージェント(Claude Code)、および将来このプロダクトに手を入れる開発者。

本書は、Utsushiの実装・設計で実際に発生した不具合・設計ミス・検出漏れを、原因と対応、そして再発防止のためにレビュー時に確認すべき観点とともに記録したものである。**個々の技術的な結論(採用した仕様・上限値など)は`.kiro/specs/*/design.md`や`docs/帳票定義スキーマ.md`が正であり、本書はそれらに至った失敗の経緯を残す場所**である。矛盾が生じた場合は本書ではなく設計書側を更新すること。

## 使い方

- 新しい実装に着手する前に、関連するレイヤー(Parsing/ReportDefinition/Substitution/Layout/Rendering)の節を一読し、同種の失敗を繰り返していないか確認する。
- `code-reviewer`・`layout-fidelity-reviewer`・`security-reviewer`・`test-writer`は、着手前に本書の該当節を読み込む(各サブエージェント定義に明記)。
- 新しい失敗事例(コードレビューで見つかった不具合、仕様との食い違い、テストで検出できなかった回帰など)が見つかったら、**修正と同じコミット/PRで**該当する節に追記する。過去の追記はすべて実際のコミット(ハッシュ)に基づく。推測や一般論は書かない。
- 各事例は「発見の経緯」「原因」「対応」「教訓」の4項目で統一する。教訓は次に同種の変更をする人・レビューする人が具体的なチェック項目として使えるように書く。

## 1. Layout/Renderingレイヤー(レイアウト忠実性)

本プロダクトのリスクが最も高い領域。`layout-fidelity-reviewer`が重点的に確認する。

### 1.1 結合セルの罫線がアンカーセルの書式だけで決まり、右端・下端の罫線が欠落する

- **発見の経緯**: コードベース調査で疑わしい箇所を洗い出し、実際にテストで再現した(意図的なバグ探しの過程で発見。ユーザー報告ではない)。
- **原因**: 結合セルの罫線描画が、結合範囲の左上(アンカー)セルの`BorderSet`だけを参照していた。Excelでは結合範囲の右端列・下端行のセルが持つ罫線がそのまま表示されるが、アンカーセルにその罫線が設定されていない場合は描画されなかった。
- **対応**: 結合範囲の外周4辺それぞれについて、対応する端のセルの罫線を参照するように修正。改ページをまたぐ場合は、そのページに実際に含まれる辺だけを描画する。
- **教訓**: 結合セルに関する処理を書く/レビューするときは「アンカーセルの書式で代表させてよいプロパティ(値・配置など)」と「結合範囲の外周セルごとに個別に見るべきプロパティ(罫線)」を混同していないか確認する。
- **参照**: `bc556ea`

### 1.2 改ページをまたぐ結合セルで、両方のページに同じテキストが重複表示される(未解決)

- **発見の経緯**: コードを読み直す中で見つけたExcelとのフィデリティ上の差異(実装後の設計レビューで発覚。バグ報告ではなく、意図的な仕様確認)。
- **原因**: 結合範囲がページ境界をまたぐ場合、現状は「そのページに見えている部分」を独立した矩形として扱ってテキストを配置する。Excelは結合範囲全体を基準にテキストを配置してからページ境界で切り取るため、両ページに同じ文字列がそのまま現れてしまう。
- **対応**: 未対応。印刷タイトル行にある結合セル(各ページへの繰り返しが正しい仕様)と区別が必要なため、対象帳票で実際に「本文中の結合セルが改ページをまたぐ」ケースが確認されてから実装する方針とし、`design.md`の未決事項に記録した。
- **教訓**: 「結合セルが改ページをまたぐ」帳票定義・テンプレートを新しく追加する場合は、この既知の差異が実害になるかどうかを必ず確認する。実害があると分かった時点で、これを未決事項のままにせず実装に着手する。
- **参照**: `df93280`、`.kiro/specs/excel-report-pdf-conversion/design.md`の未決事項

### 1.3 必須置換フィールドのセルが印刷範囲外だと、値はセットされてもPDFに出力されず静かにデータが欠落する

- **発見の経緯**: コードベース調査で疑わしい箇所を実際にテストで再現。
- **原因**: `Substitution`レイヤーは印刷範囲を意識せず値をモデルにセットする。印刷範囲(印刷タイトルの行/列を含む)外のセルはLayoutレイヤーで単純に描画対象から除外されるため、必須フィールドであっても例外にならず、PDFには何も出ない状態になっていた。
- **対応**: 必須の置換フィールドが印刷範囲の外にある場合、`LayoutComputationException`を送出するように変更。要件2.6として要件化。
- **教訓**: 「値はモデルに正しくセットされている」ことと「PDFに実際に描画される」ことは別の保証であり、印刷範囲・印刷タイトルのように「一部のセルを意図的に描画しない」機構がある場合は、その機構と必須フィールドの整合性を明示的にテストする。**サイレントな欠落は例外より危険**という前提で設計する。
- **参照**: `bc556ea`

### 1.4 印刷タイトルの行/列が印刷範囲の外にあると出力されない

- **原因**: 印刷タイトル行/列の描画を印刷範囲内のセルに限定してしまっていた。Excelでは印刷範囲と独立にタイトル行/列を各ページへ繰り返す仕様である。
- **対応**: 印刷タイトルの行/列は印刷範囲の内外に関わらず描画するよう修正。
- **教訓**: 「印刷範囲」「印刷タイトル」「結合セル」など、Excelの複数のレイアウト機構が絡む処理では、それぞれの機構の適用範囲(どのセル集合に対して有効か)を仕様書(ExcelのUI仕様)に立ち返って個別に確認する。片方の機構の実装をもう片方の制約と誤って混同しやすい。
- **参照**: `bc556ea`

### 1.5 ヘッダー/フッターの「文書と一緒に拡大縮小する」設定が、文字サイズだけでなく余白位置まで縮小してしまう

- **原因**: `scaleWithDoc`の適用対象を文字サイズと余白位置(物理的な用紙端からの距離)の両方に及ぼしていた。Excelでは文字サイズのみが対象で、余白位置(ヘッダー/フッターの配置そのもの)は印刷倍率の影響を受けない。
- **対応**: 余白位置の計算から`scaleWithDoc`によるスケーリングを除去。
- **教訓**: Excelの「拡大縮小」系オプションは、どのプロパティに効くかが名前から類推しにくい(このケースでは「文書と一緒に」という名前から余白まで対象と誤解しやすい)。実装前に実際のExcelで挙動を確認するか、既存のExcel文書仕様(ECMA-376)の該当プロパティの定義を確認する。
- **参照**: `bc556ea`

### 1.6 太字の合成描画(fake bold)がPDFをType 3フォント化し、文字列検索・コピーができなくなる

- **発見の経緯**: 請求書サンプルのPDFを`pdftotext`で検証したところ、太字部分のテキストが抽出できないことに気づいた。
- **原因**: 対象フォント(MS PGothicやIPAGothicなど)が太字の字形を持たない場合、`SkiaSharp`に太字を合成させていた。合成書体はPDF上でType 3フォント(ビットマップ相当のグリフ集合)として出力され、文字列検索・コピー・テキスト抽出ができなくなる。実際、修正前の請求書サンプルは14個のType 3フォントを含んでいた。
- **対応**: フォントが実際に太字の字形を持つかをバイト列比較で判定し、実字形があればそれを使う。無ければ通常字形を使い、描画時に輪郭を塗りと一緒に描く方式(文字送り幅は変えない)で太字を再現する。斜体も`SKFont.SkewX`で幾何変形して再現する。
- **教訓**: PDF出力の「見た目の正しさ」だけでなく、「検索可能性」「テキスト抽出可能性」もレビュー観点に含める。フォント合成に頼る実装は、レンダリング結果の目視確認だけでは検出できない副作用(埋め込みフォント形式の劣化)を生みやすいため、`pdftotext`等で機械的に検証する。
- **参照**: `ad5a5d2`

### 1.7 複数の印刷範囲を1つの外接矩形として扱い、範囲の間にある行/列まで出力していた

- **原因**: 複数の印刷範囲(Excelでは非連続な範囲を複数指定できる)を、それらすべてを包含する1つの矩形として扱っていた。範囲同士の間にある行/列は本来印刷対象外だが、外接矩形に含まれるため出力されてしまっていた。
- **対応**: 印刷範囲を定義順のまま保持し、範囲ごとに独立したページ群を計算するよう変更(要件3.6)。ページ番号は範囲をまたいで通しで振る。
- **教訓**: 「複数の矩形領域」を扱う実装で、実装を簡略化するために外接矩形へ丸めてよいかどうかは、対象がExcelの印刷範囲のように「意図的に非連続である」ケースがあるかどうかで判断する。安易な単純化がスコープ外データの混入につながる典型例。
- **参照**: `61b3913`

### 1.8 描画オブジェクトの寸法上限(`MaxDrawingObjectDimensionPt`)の適用点が、印刷拡大率の前後で不統一だった

- **発見の経緯**: `layout-fidelity-reviewer`によるレビュー指摘。
- **原因**: シート直下の図形・画像には印刷拡大率(`_scale`)適用前の`widthPt`/`heightPt`に上限を適用していたが、グループ内の子要素(`ToGroupChildRect`)には適用後の最終表示サイズに上限を適用していた。同じ定数なのに適用点が違うため、印刷倍率が100%を超える帳票では上限の実効値がグループ内外で食い違っていた。
- **対応**: どちらも印刷拡大率適用後の最終的な表示サイズ(`RectPt`)に対して上限を適用するよう統一。
- **教訓**: 「安全弁(上限)を追加する」実装は、既存の類似コードパス(このケースではグループ内子要素の変換ロジック)がすでに同じ種類の上限を持っていないか確認し、適用点(どの単位系・どの変換段階の値に対して適用するか)を必ず揃える。上限値だけ揃えて適用点がずれると、意味のない安全弁になる。
- **参照**: `343ae19`

### 1.9 グループ内図形のテキスト余白・フォントサイズが、グループ自身のリサイズ比率を考慮していなかった

- **発見の経緯**: `layout-fidelity-reviewer`によるレビュー指摘。
- **原因**: グループ化した図形をExcel上でリサイズ(拡大・縮小)すると、グループ内の各子図形は`scaleX`/`scaleY`で座標変換されるが、子図形内のテキスト余白(`ShapeTextPaddingPt`)とフォントサイズはこのリサイズ比率を反映していなかった。大きく縮小されたグループでは、テキストが矩形からはみ出す、または極端に大きく表示される問題につながる。
- **対応**: グループのリサイズ比率(`scaleX`と`scaleY`の幾何平均)を`groupScale`として、テキスト余白とフォントサイズの計算に追加で反映するようにした。
- **教訓**: 座標変換(スケール)を伴う入れ子構造(グループ内図形)を実装する際は、「位置とサイズ」だけでなく「その中の派生的な数値(余白・フォントサイズなど)」もスケールの対象に含めるべきかを個別に確認する。座標だけスケールしてスタイル値を据え置くと、ネストが深くなるほど見た目の破綻が大きくなる。
- **参照**: `343ae19`

### 1.10 フォントに字形の無い文字(外字・絵文字)が、豆腐(□)のまま例外にならずにPDFへ出力される

- **発見の経緯**: 主用途(宛名・住所の差し込み)を想定した品質確認で、請求書サンプルの宛名に「𠮷野家」「😀」を差し込み、`pdftoppm`で画像化して目視したところ豆腐になっていた(意図的な品質確認。ユーザー報告ではない)。
- **原因**: `FontResolver`のフォールバックは「フォントのファミリ自体が見つからない」場合だけを扱い、文字ごとに字形があるかは確認していなかった。字形の無い文字は glyph 0(.notdef)として描画され、アウトライン出力では空白になって消える。
- **対応**: `SkiaPdfRenderer.DrawText`(セル・ヘッダー/フッター・図形内テキストの共通経路)で描画前に`SKFont.GetGlyph`を確認し、`MissingGlyphException`を送出する(要件5.5)。`PdfRenderOptions.MissingGlyphs`で従来の動作も選べる。
- **教訓**: 「フォントがある」ことと「その文字の字形がある」ことは別の保証である。人名・地名の外字は差し込み値に普通に現れるため、フォントの有無の検証(`FontNotAvailableException`)だけで安心しない。見た目の欠落は`pdftotext`では検出できない(抽出結果には元の文字が出る)ので、画像化して確認するか、字形IDで機械的に検証する。
- **参照**: `6735b06`

### 1.11 折り返した差し込み値がセルの高さを超えると、下揃えのセルでは先頭の行から黙って消える

- **発見の経緯**: 1.10と同じ品質確認でのコード調査。
- **原因**: 折り返し表示はセルの矩形で切り取る(Excelと同じ)。縦位置が「下揃え」(Excelの既定)だと、行数が多いほど1行目がセルの上端より上に配置されて切り取られる。住所では都道府県・市区町村という最も重要な部分が欠ける。
- **対応**: 差し込み値のセル(`ReportModel.SubstitutedCells`)に限り、行の上下中心がセル外に出る行があれば`LayoutComputationException`とする(要件2.14)。テンプレート自身の文字列は人がExcelで確認済みのため、Excelと同じ切り取りのままとした。
- **教訓**: Excelと同じ挙動(忠実性)であっても、その入力を人が確認していない経路(差し込み値)ではサイレントな欠落になりうる。「Excelと同じだから正しい」で止めず、入力の出どころ(テンプレートか、呼び出し元のデータか)で扱いを分ける。
- **初版の不備(レビューで発見)**: 初版(`6735b06`)は「行の中心がセル内なら表示扱い」という緩い閾値で、1行用の高さに2行を入れて1行目の字面が6割切れる典型例を見逃していた。また、結合範囲が改ページ・印刷範囲の端・非表示行にかかると「判定しない」としたため、その場合は検出そのものが抜けていた。さらに非表示行・幅0の列にある差し込みセルも素通りしていた(`layout-fidelity-reviewer`・`code-reviewer`指摘)。判定をセル(結合範囲全体)の本来の大きさで行い、閾値を「字面の4分の1を超えてはみ出す」に改めた。**欠落検出に「この場合は判定しない」という例外を設けると、それ自体が新しい静かな欠落の経路になる**。判定を省く条件を作る前に、省かずに済む基準(ここでは見えている矩形ではなく本来の大きさ)が無いかを先に検討する。
- **参照**: `6735b06`、`17f9777`

### 1.12 折り返しがUTF-16の1単位ごとで、サロゲートペアの途中で改行されうる

- **原因**: `WrapLines`が`foreach (var c in text)`で`char`単位に幅を測って折り返していたため、「𠮷」や絵文字、異体字セレクタ付きの文字が行をまたいで分割されえた。
- **対応**: `StringInfo.GetTextElementEnumerator`による書記素クラスタ単位の折り返しにした(要件4.6)。あわせて、CR単独が改行にならない、折り返し表示でないセルで改行文字が字形として描画される、という改行まわりの不整合も解消した(要件4.7)。
- **教訓**: 文字列を「1文字ずつ」処理するコードでは、`char`がUTF-16の1単位であり利用者の認識する1文字ではないことを確認する。テストデータに漢字・かなしか使わないと検出できないため、サロゲートペア・結合文字を含むケースを必ず用意する(なお、孤立サロゲートをxUnitの`InlineData`に文字列で書くと直列化でU+FFFDに置き換わるため、UTF-16の単位の配列から組み立てる)。
- **参照**: `6735b06`

### 1.13 対応するUnicodeの無い字形があると、PDFの文字列抽出がその位置で途切れる

- **発見の経緯**: 異体字(要件11.3)の実装後、住所「東京都葛󠄀飾区…」を含むPDFを`pdftotext`で確認したところ「東京都」で行が終わっていた(描画は正しかった)。
- **原因**: 異体字の字形は`cmap`から引けない(1文字1字形のため)。サブセットの`cmap`にその字形の対応を載せていなかったため、SkiaSharpがToUnicodeでその字形をU+0000に対応づけ、`pdftotext`はそこで行の抽出を打ち切った。
- **対応**: 異体字の字形も基底文字に対応づけて`cmap`に載せた。同じ文書で通常の字形と異体字を両方使う場合は、同じ書体の別のサブセットに分けて、どちらも基底文字として抽出できるようにした。
- **教訓**: PDFの「見た目」と「文字列抽出」は別々に壊れる(1.6も同じ型)。字形番号で直接描く実装を加えたら、描画結果の画像確認とは別に、`pdftotext`で抽出結果を必ず確認する。ToUnicodeの欠落は抽出結果の該当文字だけでなく、行の残り全体を失わせることがある。
- **参照**: `6975579`

### 1.14 フォントを作り直す(サブセット化)と、fontconfig が合成していた斜体の傾きが失われる

- **発見の経緯**: `layout-fidelity-reviewer`が変更前後のPDFを画素単位で比較し、Bold のファイルはあるが Bold Italic の無い書体(DejaVu Sans、BIZ UDPゴシック)の太字斜体だけが、斜体でなくなっていることを見つけた。
- **原因**: 太字斜体を求めると fontconfig は Bold のファイルに斜体の傾き(`FC_MATRIX`)を付けて返す。従来は「通常字形と別ファイルなら要求どおりの実字形」とみなして合成を行わず、傾きは SkiaSharp が付けていた(PDF上は Type 3 になっていた)。サブセット化で書体を表から作り直すと、この傾きは書体のデータに含まれないため失われた。
- **対応**: 別ファイルの書体が返った場合は、OS/2(無ければ head)の書体情報でデータ自体が持つ太字・斜体を読み、足りない装飾だけを描画側で合成するようにした。
- **教訓**: 書体(`SKTypeface`)の「見た目」は、フォントのデータだけでなく実行環境(fontconfig)が付けた変換を含みうる。書体を表から作り直す・別の経路で読み直す変更では、元の書体が持っていたがデータに無い性質(合成された装飾など)が落ちないかを確認する。変更前後の出力の画素単位の比較は、この種の退行を見つける確実な方法である。
- **参照**: `eca1885`

### 1.15 Excelの「線吹き出し」が対応済み一覧から漏れており、`unsupportedElements: "error"` の帳票で変換が止まった

- **発見の経緯**: 利用者が自社のExcelファイルを変換したところ、`UnsupportedWorkbookElementException: シート 'Sheet1' の図形のプリセットジオメトリ 'BorderCallout2' には対応していません` で変換が止まった。
- **原因**: 対応済みプリセットの一覧に `callout1`〜`3` を入れた際、これがExcelでよく使う枠付きの線吹き出しだと取り違えていた。ECMA-376上、枠付きの線吹き出しは `borderCallout1`〜`3` であり、`callout1`〜`3` は本体の枠線を持たない(`stroke="false"`)線吹き出しである(Excelの画面上の名前はバージョンで異なりうるため、名前ではなく保存された `prst` で区別する)。このため最もよく使う「線吹き出し」が対応外になっていた。さらに `callout1`〜`3` には本体の枠線を描いており(ECMA-376では枠なし)、引き出し線の位置も調整ガイドを読まない固定形状だった。
- **対応**: 線吹き出し12種(`callout`/`borderCallout`/`accentCallout`/`accentBorderCallout` の1〜3)を1つのロジックで描くようにした。枠線・強調線の有無を種類ごとに分け、引き出し線の頂点は調整ガイド(`adj1`=y1, `adj2`=x1, …)から求める(要件10.14)。
- **教訓**: プリセット名(`prst`)とExcelのUI上の名前は一致しない。対応済みにする前に、**Excelで実際にその図形を描いて保存したファイルの `prst`** を確かめる。`line`(「図形 → 線 → 直線」)の漏れ(tasks.md 22.9)と同じ型の再発である。
- **参照**: `f8f77f9`

## 2. Substitution/Parsingレイヤー(データの静かな欠落・書式の上書き)

「例外にならずに値やスタイルが失われる」パターンが繰り返し見つかっている。`code-reviewer`が重点的に確認する。

### 2.1 結合セル範囲の非アンカー位置をセル番地直接指定で上書きすると、値は反映されるがPDFには一切出力されない

- **発見の経緯**: コードレビュー(commit `b284442`の直後のレビュー)で発見。
- **原因**: Layoutレイヤーは結合セル範囲のアンカー(左上)セルの値しか描画しない。セル番地直接指定オーバーライドで非アンカー位置に値を設定すると、モデル上は値が反映されるが、描画時には無視される。
- **対応**: `ApplyCellOverrides`の適用時点で対象セルが結合セル範囲の非アンカー位置かどうかを検出し、`NonAnchorMergedCellOverrideException`を送出する(要件2.9)。
- **教訓**: 「モデルに値がセットされること」と「PDFに描画されること」の間にギャップがある箇所(1.3と同種のパターン)は、新しい入力経路(このケースではセル番地直接指定という新機能)を追加するたびに再確認する。同じ種類の落とし穴に複数の入力経路(帳票定義キー経由、セル番地直接指定経由)から到達しうる。
- **参照**: `25594cd`

### 2.2 セル番地直接指定と帳票定義キーのoverflow設定が競合すると、古い設定が残る

- **原因**: 同じセルが帳票定義の置換キーにも登録されて`overflow`が明示されている場合、セル番地直接指定で値を上書きしても、`OverflowByCell`の既存エントリが削除されずに残っていた。「Excel側のセル書式に従う」という設計と矛盾する状態になっていた。
- **対応**: セル番地直接指定で上書きする際、対象セルの既存の`OverflowByCell`エントリを削除するように修正。`CellSubstitutor.ApplyCellOverrides`を`Apply`と同様の「検証してから適用」の二段階構成に揃えた。
- **教訓**: 複数の入力経路(帳票定義キー、セル番地直接指定)が同じ内部状態(`OverflowByCell`)を更新しうる設計では、後から適用される経路が前の経路の状態を正しく上書き・削除できているかをテストする。「片方だけ試験して問題ない」は不十分で、**適用順序を変えた組み合わせ**を試験する。
- **参照**: `25594cd`

### 2.3 `overflow`未指定時、既定値が明示指定と区別できずExcel側のセル書式(wrapText/shrinkToFit)を上書きしてしまう

- **発見の経緯**: `docs/帳票定義スキーマ.md`のドキュメントを実装と突き合わせる過程で発見(ドキュメントレビューが実装バグの発見につながった例)。
- **原因**: `substitutionFields[].overflow`を省略した場合、JSONリーダーが既定値として`OverflowBehavior.Overflow`を返し、それがそのまま`OverflowByCell`に記録されていた。Layoutは`OverflowByCell`に値があれば無条件に優先するため、テンプレート側で`wrapText`/`shrinkToFit`を設定してあるセルでも、置換した瞬間にその書式が無効化されていた。
- **対応**: `SubstitutionFieldDefinition.Overflow`を`nullable`にし、「未指定」と「明示的に指定」を区別できるようにした。未指定のセルは`OverflowByCell`に載せず、Excel側のセル書式をそのまま使う。
- **教訓**: 「JSONスキーマ上のオプショナルなプロパティ」を読み込む際、プログラミング言語のデフォルト値(この場合はenumの既定値)をそのまま「未指定時の挙動」として使うと、「明示的にデフォルト値を指定した場合」と区別できなくなる。オプショナルなフィールドは`nullable`型で読み込み、「未指定」を独立した状態として扱う。**ドキュメント(スキーマ定義書)と実装を突き合わせるレビューは、ドキュメントの誤りだけでなく実装の誤りも見つけられる**ことを踏まえ、`doc-reviewer`のレビュー時にも実装との整合を意識する。
- **参照**: `53d114e`

### 2.4 数値書式の桁区切りカンマが小数点より後にあると、千/百万単位スケーリングが効かず不要なカンマが残る

- **原因**: `#,##0.0,`のように桁区切りカンマが小数点の後にあるパターンを、スケーリング(千単位・百万単位表示)のトリガーとして認識できていなかった。
- **対応**: 小数点の前後どちらにあるカンマもスケーリングのトリガーとして扱うよう修正。
- **教訓**: Excelの数値書式コードのパターンマッチングを自前実装する場合、ECMA-376の書式コード仕様を確認するだけでなく、「小数点の前後」「桁区切りの位置」のように、見た目は同じ記号でも位置によって意味が変わる要素を網羅的に洗い出す。テストケースは「小数点あり/なし × カンマが前/後」の直積で用意する。
- **参照**: `bc556ea`

### 2.5 帳票定義のSheetNameが実シート名と不一致のとき、経路によって例外の種別・Stageが食い違う

- **原因**: `ReportPdfConverter`経由では`InvalidExcelFileException(Stage=Parsing)`になる一方、`ReportModelBuilder`が用意する`ReportStructureMismatchException(Stage=ReportDefinition)`には到達しないという食い違いがあった。
- **対応**: 経路によらず一貫した例外種別・Stageになるよう修正し、実在するシート名一覧もエラーメッセージに含めるようにした。
- **教訓**: 例外階層(`UtsushiException`)を設計する際、「同じ論理的な失敗(シート名不一致)が複数のコードパスから起こりうるか」を洗い出し、経路によって例外の型・`Stage`が変わらないことをテストする。呼び出し元(ファサード経由か、下位レイヤー直接呼び出しか)によって挙動が変わる例外設計は、利用者を混乱させる。
- **参照**: `bc556ea`

### 2.6 差し込み値のタブ・`null`・必須キーの空文字が、例外にならずに豆腐・空欄のままPDFになる

- **発見の経緯**: 1.10と同じ品質確認。`InvoiceNo`に`"INV\t0001"`を渡すと豆腐になり、必須キーに`null`や空文字を渡すと必須チェック(要件2.4)を通過して空欄のまま出力された。
- **原因**: `CellSubstitutor`は値の中身を一切検証せず、必須チェックは`ContainsKey`(キーの有無)だけだった。任意キー・セル番地直接指定のセルが印刷範囲外にある場合の検出(1.3の横展開)も、必須キーにしか適用されていなかった。
- **対応**: 制御文字・孤立サロゲート・`null`を`InvalidSubstitutionValueException`に、必須キーの空文字・空白のみを`RequiredSubstitutionValueMissingException`にし、CRLF/CRをLFへ統一した(要件2.10〜2.12)。印刷範囲外の検出を、空でない値を差し込んだ全セルへ広げた(要件2.13)。
- **教訓**: 「キーが渡されたか」と「意味のある値が渡されたか」は別の検証である。また1.3のような欠落検出を追加したときは、同じ欠落に到達する他の入力経路(任意キー・セル番地直接指定)にも横展開されているかをその場で確認する(まとめの観点1・2の再発)。
- **参照**: `6735b06`

## 3. エラーハンドリング・パイプライン全体

### 3.1 PDFのアトミック書き込みが`SkiaPdfRenderer`経由でのみ保証され、差し替えたレンダラー実装では保証されない

- **原因**: 一時ファイル経由のアトミックな書き込み(正常終了時のみ最終出力先へ確定させる、要件5.4)が`SkiaPdfRenderer`の実装に直接埋め込まれており、`IPdfRenderer`の別実装に差し替えた場合はこの保証が失われる設計になっていた。あわせて、一時ファイル名が固定されていたため、PDF生成を同時実行すると正常な出力を別のプロセスが消しうる競合状態もあった。
- **対応**: アトミックな書き込みを`AtomicFileWriter`という共通コンポーネントに切り出し、`IPdfRenderer`の実装に依存しない形にした。一時ファイル名も一意になるよう修正。
- **教訓**: インターフェース(`IPdfRenderer`)で抽象化した処理に「実装によらず満たすべき契約」(この場合はアトミック性)がある場合、その契約をインターフェースの実装者に委ねてはいけない。契約を満たす共通コンポーネントを用意し、インターフェースの外側(呼び出し元)で保証する設計にする。
- **参照**: `bc556ea`

### 3.2 `ConvertToFile`の入力ファイルオープン失敗が、例外の種類によって`UtsushiException`階層に統一されていなかった

- **原因**: `IOException`/`UnauthorizedAccessException`は`UtsushiException`に変換していたが、パス文字列の形式不正(コロンを含む等)で`File.OpenRead`が投げる`NotSupportedException`は変換対象から漏れていた。
- **対応**: `NotSupportedException`も変換対象に追加(`ArgumentException`/`ArgumentNullException`のような契約違反は意図的に対象外のまま)。
- **教訓**: 「特定のAPI呼び出しが投げうる例外の一覧」を基準に例外変換のコードを書く場合、そのAPIのドキュメント(`File.OpenRead`など)に列挙されている例外を実際に全種類確認する。一般的な例外(`IOException`)だけを想定してレビューを終えると、そのAPI固有の例外(`NotSupportedException`)を見落とす。
- **参照**: `4c9a148`

## 4. セキュリティ・DoS対策(上限チェックの後追い発見)

詳細な経緯は`.claude/agents/security-reviewer.md`の「横断確認」節、および`.kiro/specs/excel-report-pdf-conversion/design.md`の「信頼できない入力に対する安全弁 一覧」を参照。ここでは事例としての要点のみ記録する。

### 4.1 上限チェックが、画像・図形 → 結合セル → 共有文字列/セル数/ZIP総サイズの順に、別々の増分として後追いで発見された

- **発見の経緯**: 画像・図形の個数/サイズ上限を追加してレビューを受けた際、`security-reviewer`が新たに「結合セルの件数には上限が無い」ことを指摘。その修正をレビューした際に、今度は「共有文字列数・シート内セル数・ZIP展開後総サイズには上限が無い」ことが指摘された。同じパターンの上限漏れが3回に分けて後追いで見つかった。
- **原因**: 各レビューが直前の差分(diff)の範囲に閉じてしまい、`src/Utsushi.Parsing/OpenXml/`配下の「上限が無いループ」を一度に網羅的に洗い出す横断確認をしていなかった。個々の指摘自体は正確だったが、発見の順序がプロセス上非効率だった。
- **対応**: `security-reviewer.md`に、差分に閉じず`foreach`/`Elements<...>()`ループを機械的に洗い出す横断確認を必須のレビュー観点として追加した(2026年9月のセッションでのプロセス改善)。
- **教訓**: 「型として同じ種類の問題(上限チェック漏れ)」を見つけるレビューは、差分駆動ではなく対象コード全体を横断する棚卸しとして行う。1件見つかったら「同じ種類の問題が他にもないか」を必ずその場で確認する。
- **参照**: `343ae19`、`57450d5`

### 4.2 フォントの表の自前解析でも、件数の上限漏れ・例外の漏れが見つかった(4.1の型の再発)

- **発見の経緯**: `security-reviewer`が、細工したフォントで`TrueTypeSubsetter`・`VariationSequenceTable`を実行して確認した。
- **原因**: 表の件数・オフセットを表の長さと照合せず、`cmap` format 14 は複数のレコードが同じ表を指すことを許したまま毎回読んでいた(300KBの表で約6GB・30秒)。`loca` の範囲が重なるフォントではサブセットが元より大きく膨らんだ(数百MB、`IOException`)。SkiaSharp の`GetTableData`は失敗時に基底の`Exception`を投げ、Layout段階(計測)では`UtsushiException`階層の外へ漏れた。
- **対応**: 件数を読む前に残りバイト数と照合し、共有された表は一度だけ読み、読み取る総数を表の長さで打ち切った。出力が元より大きくなったらサブセット化を諦める。`TryGetTableData`/`TryGetTableTags`を使う。
- **教訓**: 「フォントは信頼できる入力」という前提でも、利用者が登録するファイルは壊れうる。バイナリ形式を自前で解析するコードを追加したら、Excel(Parsingレイヤー)と同じ観点(件数・オフセットの検証、共有された構造の多重展開、捕捉されない例外の種類)で横断確認する。外部ライブラリのAPIが投げる例外の種類は、ドキュメントではなく実装(ここでは SkiaSharp の`GetTableData`)で確かめる(3.2と同じ教訓)。
- **参照**: `eca1885`

## 5. テスト・ゴールデンテストの検出漏れ

### 5.1 ゴールデンスナップショットのImageCommandフォーマッタが回転角を出力しておらず、回転バグを検出できない

- **発見の経緯**: 画像回転(`&rot`)対応のレビューで、`code-reviewer`と`layout-fidelity-reviewer`の両方が独立に指摘。
- **原因**: `GoldenSnapshot`の`ImageCommand`フォーマッタが`rotation`を出力していなかった(`ShapeCommand`/`ConnectorCommand`/`GroupCommand`は出力済みだった)。そのため回転角0度と20度が同一のスナップショット行になり、回転の実装にバグがあってもゴールデンテストが検出できない状態だった。
- **対応**: `Shape`/`Connector`/`Group`と同様に`rotation`を出力するよう修正し、ゴールデンファイルを再生成した。
- **教訓**: 新しいプロパティ(このケースでは`RotationDegrees`)を既存の型(`ImageCommand`)に追加するとき、その型を扱う描画コード側だけでなく、**テストの検証コード(ゴールデンスナップショットのフォーマッタ)側にも新しいプロパティを反映しているか**を確認する。同じ種類の型(`ShapeCommand`等)に既に対応済みのプロパティがある場合、新しい型でも横並びで対応漏れがないか比較する。「テストがグリーンである」ことは、そのテストが実際に対象の変更を検知できることを意味しない。
- **参照**: `24ae54c`

### 5.2 PDF描画のテストが、代替フォントで日本語を豆腐として描画したままグリーンだった

- **発見の経緯**: 字形の欠落検出(1.10)を実装したところ、既存の`SkiaPdfRendererTests`とゴールデンテストのPDF生成が一斉に失敗し、CI相当の環境(日本語フォント無し)では日本語が「DejaVu Sans」で描画されていた、つまり豆腐のPDFを生成して合格していたことが分かった。
- **原因**: 描画テストは`FontResolverOptions.AllowFallback()`(代替フォント名の指定なし)で既定書体にフォールバックし、PDFの構造(ページ数・フォント形式)だけを検証していた。字形の有無は誰も検証していなかった。
- **対応**: 構造だけを検証するテストでは`MissingGlyphPolicy.Render`を明示して「字形は検証対象外」であることをコード上で表明し、字形の欠落検出は専用のテスト(`MissingGlyphTests`)で検証するようにした。
- **教訓**: テストの前提(ここでは「CIに日本語フォントが無い」)が出力の品質を黙って下げている場合、それを暗黙のまま放置せず、テストコード上で明示的なオプトアウトにする。明示されていれば、次にそのテストを読む人が「このテストは字形を保証しない」と分かる。
- **参照**: `6735b06`

### 5.3 PDFの生のバイト列に文字列が含まれるかを見るテストが、埋め込みフォントのデータに偶然一致して合格していた

- **発見の経緯**: フォントのサブセット化(要件11.5)を実装したところ、`図形内テキストはPDFに描画される`が失敗した。
- **原因**: テストは描画した"OK"がPDFの生のバイト列に含まれるかを見ていた。PDFのテキストは字形番号(Identity-H)で書かれ、しかも圧縮されているため、描画した文字列はそのままの形では現れない。一致していたのは、丸ごと埋め込まれていたフォントのデータの中にたまたま"OK"というバイト列があったためで、テストは図形内テキストを描画しなくても合格する状態だった。
- **対応**: 文字を描いた場合だけフォント(`/FontFile2`)が埋め込まれることを、テキストの無い図形と比べて確かめる形にした。
- **教訓**: 「生成物に文字列が含まれる」形の検証は、その文字列が生成物の中でどういう形で表現されるか(符号化・圧縮)を確かめてから書く。検証したい変更を元に戻してもテストが失敗するかを一度確かめれば、このような偶然の合格は見つけられる(5.1と同じ「テストが対象の変更を検知できるか」の問題)。
- **参照**: `6975579`

## 6. 環境・ビルド・ドキュメント

### 6.1 利用側の開発環境(Visual Studio 2019)のC#バージョン制約に後から気づき、大規模な書き直しが発生した

- **発見の経緯**: 呼び出し元プロダクトの開発環境がVS2019(C# 9.0までしかサポートしない)であることが判明。
- **原因**: 当初`LangVersion`を10.0に設定して実装を進めていたため、C# 10専用の機能(`record struct`、file-scoped namespaceの記法選択の余地はあるがブロック形式への統一が必要)を使用していた。利用側の制約を実装開始前に確認していなかった。
- **対応**: `Directory.Build.props`の`LangVersion`を9.0に変更し、全76ファイルのfile-scoped namespaceをブロック形式に変換、`FontMetrics`を`record struct`から`readonly struct + IEquatable<T>`に書き換えるなど、影響範囲全体を修正した。VS2019用のクラシックソリューションファイルも別途用意した(後に `.slnx` を削除し、ルート直下の `Utsushi.sln` に一本化)。あわせて、VS2019と同じコンパイラ(Roslyn 3.11)・.NET 5 SDKでのビルドをCIのジョブに追加した(.NET 5 SDKのWindowsジョブはこの環境では実行できず、CIの初回実行で確認する)。
- **教訓**: ライブラリとして提供するプロダクトでは、**自分たちの開発環境の言語バージョンではなく、利用側(呼び出し元)の開発環境の制約**を実装着手前に確認する。`.kiro/steering/tech.md`のような常時適用ドキュメントに技術制約を書く際は、「このプロダクト自身がビルドできる最新バージョン」ではなく「利用側が要求する最低バージョン」を基準にする。
- **参照**: `9fe607c`

### 6.2 ドキュメントに書いたコマンド例(`dotnet sln`)が実機で失敗する誤りだった

- **発見の経緯**: `doc-reviewer`による技術的記載の裏取り(実際にコマンドを実行して検証する観点)で発見。
- **原因**: `dotnet sln add/remove`の`<PATH>`引数はカレントディレクトリ基準の相対パスであり、slnファイルの場所基準ではないにもかかわらず、`../<csproj>`という(slnファイル基準の)誤ったコマンド例を`structure.md`に記載していた。
- **対応**: 実際に実行して成功する形にコマンド例を修正。
- **教訓**: **ドキュメント中のコマンド例は、書いた本人の想像ではなく実際に実行して検証してから記載する**(`doc-reviewer`のレビュー観点そのもの)。この事例は`doc-reviewer`が実際に機能した好例であり、今後もコマンド例を追加・変更する際は同様の裏取りを省略しない。
- **参照**: `b04d5f9`

### 6.3 指定ブランチが既にマージ済みの状態で次の増分を始めると、見せかけのマージコンフリクトが発生する

- **発見の経緯**: 2026年9月22日のセッションで、1つの指定ブランチを複数PRで使い回す運用において3回連続で発生。
- **原因**: squash mergeで`main`に取り込まれたコミットと、ローカルブランチに残る取り込み前のコミットは内容が同じでも別のコミットオブジェクトになるため、次の増分をその上に積むと3-way mergeの共通祖先が実際より古い地点まで遡り、見せかけの衝突が検出される。
- **対応**: `git diff <ブランチ先端> origin/main --stat`が空であることを確認したうえで、`git fetch origin main && git checkout -B <ブランチ名> origin/main`でブランチを作り直し、新しい変更をコミットしてから`--force-with-lease`でpushする。詳細な手順は`docs/開発環境メモ.md`を参照。
- **教訓**: ブランチ運用上の制約(1つのブランチを複数PRで使い回す)に起因する問題は、コードの不具合ではないため見落とされやすい。「症状(non-fast-forward、`mergeable_state: "dirty"`)」から「原因(squash mergeによるコミットオブジェクトの相違)」への対応関係を一度言語化しておくことで、次回以降は診断コストがゼロになる。
- **参照**: `docs/開発環境メモ.md`「6. Git: 指定ブランチが既にマージ済みの状態で次の増分を始める場合」

## まとめ: レビュー時に繰り返し確認すべき観点

上記の事例から抽出した、複数回登場している共通パターンは次の3つである。

1. **サイレントなデータ欠落**(1.3, 1.10, 1.11, 2.1, 2.2, 2.3, 2.6): 例外にならずに値・書式が失われるパターン。新しい入力経路や新しいオプションを追加するたびに、既存の内部状態(`OverflowByCell`等)や既存の描画対象判定(印刷範囲・アンカーセル等)との相互作用を確認する。
2. **横並びの型・経路の対応漏れ**(1.8, 2.5, 2.6, 5.1, 5.3): 同じ種類の型・経路が複数存在する場合(`ShapeCommand`/`ImageCommand`、帳票定義キー/セル番地直接指定、`ReportPdfConverter`経由/直接呼び出し)、片方にだけ対応して他方への横展開を忘れるパターン。新機能・修正を1箇所に適用したら、同じ種類の他の箇所を必ず横並びで確認する。
3. **差分駆動レビューの限界**(4.1, 4.2): 同じ種類の問題(上限チェック漏れ)を見つけるレビューは、差分に閉じず対象コード全体を横断して棚卸しする。
