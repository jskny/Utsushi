# 要件定義書: 自社帳票のExcel→PDF変換

## はじめに

自社で運用している既知のExcel帳票テンプレートを対象に、(1) 指定セルへの文字列置換を行った上で、
(2) Excel上のレイアウト(改ページ・印刷範囲・列幅/行高・結合セル・フォント・罫線・配置)を崩さずに、
(3) 商用ライブラリおよびOffice Interopに依存しない方法でPDFとして出力する機能を定義する。

任意のExcelファイルを汎用的に扱う変換エンジンではなく、あらかじめ「帳票定義」として登録された特定の帳票のみを対象とする。

## 用語

- **帳票定義**: 対象Excelテンプレート1つに対応する、印刷範囲・置換対象セル・既知の特殊処理などを記述したメタデータ。
- **置換キー**: 置換対象セルを一意に識別する論理名(例: `InvoiceNo`, `IssueDate`)。セル番地そのものではなく、帳票定義を介して間接参照する。
- **ゴールデンテスト**: レビュー済みの期待出力(PDF/描画ログ)と実際の出力を比較する回帰テスト。

## 要件

### 要件 1: 帳票定義に基づくExcelファイルの読み込み

**ユーザーストーリー:** システム開発者として、登録済みの帳票定義に従って対象Excelファイルの構造(セル値・スタイル・結合セル・ページ設定)を読み込みたい。それは、後続のレイアウト計算・PDF描画の入力データを得るためだ。

#### 受け入れ基準

1. WHEN 帳票定義に紐づくExcelファイル(.xlsx)が指定される THEN システムは Office Interopを使用せずにファイルを読み込み、内部モデルに変換する SHALL。
2. WHEN Excelファイルを読み込む THEN システムは 対象シートのセル値、数値書式、フォント(書体・サイズ・太字・斜体・色)、罫線、背景色、結合セル範囲、列幅、行高、配置(水平/垂直)を取得する SHALL。
3. WHEN Excelファイルを読み込む THEN システムは 印刷範囲(Print Area)、改ページ位置(手動・自動)、用紙サイズ、余白、印刷の向き、拡大縮小設定、タイトル行/列の固定(印刷タイトル)を取得する SHALL。
4. IF 読み込み対象のファイルが帳票定義に登録されていない、または帳票定義が期待するシート構成と一致しない THEN システムは 変換を中止し、原因を特定できるエラーを返す SHALL。
5. IF Excelファイルに帳票定義が想定していない要素(サポート外の図形・グラフ・外部参照など)が含まれる THEN システムは その要素の扱い(無視/エラー)を帳票定義の設定に従って決定する SHALL。
6. WHEN 数式を含むセルを読み込む THEN システムは 数式を評価せず、Excelがファイルに保存した計算結果の値のみを読み取る SHALL。

> 補足(要件1.6): 本プロダクトは数式計算エンジンではない(`.kiro/steering/product.md`「非対応」)。
> テンプレートをExcelで保存した時点の計算結果がファイルに残っているため、それをそのまま使う。
> 置換によって数式の入力値が変わる帳票(置換値に依存する合計欄など)は、
> 合計値そのものを置換キーとして帳票定義に登録する運用とする。

### 要件 2: 指定セルの文字列置換

**ユーザーストーリー:** システム利用者として、帳票内の特定セル(宛先名・日付・金額・番号など)をシステムが持つ値で置き換えたい。それは、テンプレートから実際の帳票を生成するためだ。

#### 受け入れ基準

1. WHEN 置換キーと置換後の文字列のペアが指定される THEN システムは 帳票定義に登録された対応セルの値のみを置換する SHALL。
2. WHEN セルの値を置換する THEN システムは 置換対象セルの既存の書式(フォント・配置・罫線・数値書式)を変更しない SHALL。
3. IF 指定された置換キーが帳票定義に存在しない THEN システムは エラーを返し、処理を中止する SHALL。
4. IF 帳票定義が必須と定義した置換キーに対応する値が渡されていない THEN システムは エラーを返し、処理を中止する SHALL。
5. WHEN 置換後の文字列がセルの表示可能幅を超える THEN システムは 帳票定義で指定された折り返し/縮小表示/はみ出し許容のいずれかの挙動に従う SHALL。
6. IF 帳票定義が必須と定義した置換キーの対象セルが、印刷範囲(要件3.1)・印刷タイトル(要件3.4)のいずれにも含まれない THEN システムは エラーを返し、処理を中止する SHALL。
7. WHEN 置換キーとは別の経路で、セル番地(A1形式)を直接指定した上書き値が渡される THEN システムは 帳票定義への登録有無に関わらず指定されたセルを置換対象とする SHALL(書式を変更しない点は要件2.2と同様)。
8. IF 直接指定されたセル番地がA1形式として解釈できない THEN システムは エラーを返し、処理を中止する SHALL。
9. IF 直接指定されたセル番地が結合セル範囲内にあり、かつ結合範囲の先頭(アンカー)セルでない THEN システムは エラーを返し、処理を中止する SHALL。

> 補足(要件2.6): 値自体は正しくセットされても、対象セルが印刷範囲・印刷タイトルの外にあると
> PDFには出力されず、値が渡されなかった場合(要件2.4)と同様に静かなデータ欠落となる。
> 印刷範囲は帳票定義の`printArea`上書きの有無やExcel側の設定によって最終的に確定するため、
> この検証はLayoutレイヤーで印刷範囲が確定した時点(要件3.1, 3.4)で行う
> (`ReportLayoutEngine.ValidateRequiredFieldsAreInPrintRanges`)。
>
> 補足(要件2.7, 2.8): 置換キー方式(要件2.1)は事前に帳票定義へ登録したセルのみを対象とするのに対し、
> この経路は帳票定義への登録有無に関わらずセル番地で直接指定できる。呼び出し元がAPIを直接呼ぶ用途、
> およびCLIの`--override`オプション経由の用途(例: 帳票定義の更新を待たずに一時的な値を
> 差し込みたい場合)を想定する。ただし対象は
> 要件1.4で登録済みと確認された帳票のシートに限られ、任意のExcelファイルを汎用的に扱うものでは
> ない(`.kiro/steering/product.md`)。未知キー検証(要件2.3)・必須キー検証(要件2.4)・
> はみ出し挙動の帳票定義指定(要件2.5)はこの経路には適用されず、はみ出し時はExcel側の
> セル書式(`wrapText`/`shrinkToFit`)にそのまま従う。同じセルが帳票定義の置換キーにも
> 登録されており、かつ`overflow`が明示されている場合、この経路で上書きすると
> その帳票定義側の`overflow`指定は取り消され、Excel側のセル書式に従う扱いに戻る。
>
> 補足(要件2.9): 結合セル範囲は先頭(アンカー)セルの値のみが描画される(要件4.3、
> `PageCommandBuilder`)。アンカー以外のセルを直接指定して上書きすると、値はモデルには
> 反映されてもPDFには一切出力されない静かなデータ欠落になるため、要件2.6と同様に
> 事前にエラーとする。

### 要件 3: 改ページ・印刷範囲に従ったページ分割

**ユーザーストーリー:** システム開発者として、Excelで印刷した場合と同じページ構成でPDFを生成したい。それは、既存の帳票運用(紙/PDF)との見た目の一貫性を保つためだ。

#### 受け入れ基準

1. WHEN 印刷範囲が設定されている THEN システムは その範囲外のセルをPDFに出力しない SHALL。
2. WHEN 手動の改ページが設定されている THEN システムは 指定された行/列の位置でページを分割する SHALL。
3. WHEN 手動の改ページが設定されていない範囲について、印刷範囲が1ページの印字可能領域(用紙サイズ・余白・拡大縮小率から算出)を超える THEN システムは Excelの自動改ページ計算と同等のロジックで行/列単位にページを分割する SHALL。
4. WHEN 印刷タイトル(先頭行/先頭列の固定)が設定されている THEN システムは 2ページ目以降にも当該の行/列を繰り返し出力する SHALL。
5. WHEN 複数ページを出力する THEN システムは 元のExcelの印刷順序設定(行優先/列優先)に従ってページ順を決定する SHALL。
6. WHEN 1つのシートに複数の印刷範囲が設定されている THEN システムは 各印刷範囲をそれぞれ独立したページ群として、定義順に出力する SHALL。
7. WHEN ページヘッダー/フッターが設定されている THEN システムは 左/中央/右の各セクションの内容を、ヘッダー余白/フッター余白の位置に出力する SHALL。
8. WHEN ヘッダー/フッターにページ番号・総ページ数・日付・時刻・シート名の書式コードが含まれる THEN システムは それらを実際の値に置き換えて出力する SHALL。
9. IF ヘッダー/フッターに「先頭ページのみ別指定」「奇数/偶数ページで別指定」が設定されている THEN システムは 各ページに対応する指定を選択する SHALL。

> 補足(要件3.6): Excel は複数の印刷範囲を「それぞれ別のページとして印刷する」。
> 範囲を包含する1つの矩形として扱うと、範囲の間にある不要なセルまで出力されてしまう。
>
> 補足(要件3.7, 3.8): 対応する書式コードは、自社帳票で使う範囲
> (セクション指定・ページ番号・総ページ数・日付・時刻・シート名・ファイル名・
> フォント指定・太字/斜体/下線)に限定する。画像(`&G`)は対象外とする。

### 要件 4: 書式(フォント・罫線・結合セル・配置)の再現

**ユーザーストーリー:** システム利用者として、PDF化後も帳票の見た目(フォント、罫線、セル結合、文字揃え)がExcel上の表示と一致していてほしい。それは、社外に提出する帳票としての品質を保つためだ。

#### 受け入れ基準

1. WHEN セルを描画する THEN システムは Excelで設定されたフォント(書体・サイズ・太字・斜体・下線・文字色)をPDF上で再現する SHALL。
2. WHEN セルを描画する THEN システムは Excelで設定された罫線(位置・太さ・線種・色)をPDF上で再現する SHALL。
3. WHEN 結合セルを描画する THEN システムは 結合範囲全体を1つの表示領域として扱い、値・書式・罫線を結合範囲に対して正しく適用する SHALL。
4. WHEN セル内のテキストを配置する THEN システムは Excelで設定された水平/垂直方向の配置(左揃え・中央揃え・右揃え・上/中央/下揃え、インデント)を再現する SHALL。
5. WHEN 列幅・行高をPDF上の寸法に変換する THEN システムは 対象帳票のフォントメトリクスに基づき、Excel表示時との誤差が許容範囲(帳票定義で定める閾値)に収まるように計算する SHALL。

### 要件 5: PDF出力

**ユーザーストーリー:** システム利用者として、変換結果を標準的なPDFファイルとして受け取りたい。それは、既存の配布・保存・印刷の仕組みでそのまま扱うためだ。

#### 受け入れ基準

1. WHEN 変換処理が完了する THEN システムは 単一のPDFファイル(複数ページの場合は1ファイル内に全ページを含む)を出力する SHALL。
2. WHEN PDFを出力する THEN システムは 元のExcelの用紙サイズ・印刷の向き・余白に対応するページサイズでPDFの各ページを生成する SHALL。
3. WHEN PDFを出力する THEN システムは 一般的なPDFビューアで表示可能な標準準拠のPDF(バージョン等はdesign.mdで定める)を生成する SHALL。
4. IF PDF生成中に回復不能なエラーが発生する THEN システムは 不完全なPDFファイルを残さず、エラーを呼び出し元に返す SHALL。

### 要件 6: エラーハンドリングと対象外入力の扱い

**ユーザーストーリー:** システム運用者として、対象外のファイルや不正な入力が渡された場合に、原因が分かる形で安全に失敗してほしい。それは、障害調査のコストを下げ、意図しない出力を防ぐためだ。

#### 受け入れ基準

1. IF 入力ファイルが有効なExcel(.xlsx)形式ではない THEN システムは 明確なエラー種別とともに処理を中止する SHALL。
2. IF 入力ファイルが破損している、またはパスワード保護されている THEN システムは 明確なエラー種別とともに処理を中止する SHALL。
3. IF 帳票定義が参照する帳票定義ファイル自体が不正(スキーマ不一致等)である THEN システムは 起動時またはロード時にエラーを検出する SHALL。
4. WHEN エラーが発生する THEN システムは どの帳票定義・どのセル・どの処理段階で失敗したかを特定できる情報をログ/例外に含める SHALL。
5. IF 入力ファイルが存在しない、またはアクセス権限がなく開けない THEN システムは 明確なエラー種別とともに処理を中止する SHALL。

### 要件 7: 無償・自己完結な技術構成

**ユーザーストーリー:** システム開発者として、追加のライセンス費用やOfficeのインストールなしに変換処理を実行したい。それは、サーバー環境での運用コストとライセンスリスクを避けるためだ。

#### 受け入れ基準

1. WHEN 依存ライブラリを選定する THEN システムは 商用ライセンス(利用に課金が発生するもの)を含まない SHALL。
2. WHEN 変換処理を実行する THEN システムは Office InteropまたはExcelアプリケーション本体のインストールを必要としない SHALL。
3. WHEN 変換処理を実行する THEN システムは Office/Excelがインストールされていないサーバー環境(CI含む)で動作する SHALL。

### 要件 8: 帳票定義による拡張性

**ユーザーストーリー:** システム開発者として、新しい帳票への対応を、既存のレイアウト計算・描画ロジックを変更せずに追加したい。それは、帳票追加のたびにコードレビュー・回帰テストの範囲が広がることを避けるためだ。

#### 受け入れ基準

1. WHEN 新しい帳票に対応する THEN システムは 新規の帳票定義データの追加のみで対応できる(共通レイヤーのコード変更を要求しない)構成を提供する SHALL。
2. IF 帳票定義で表現できない特殊なレイアウト要件が発生する THEN システムは 該当要件を明示的な仕様として `.kiro/specs/` に追記した上でのみ共通レイヤーを拡張する SHALL。
3. WHEN 帳票定義を追加する THEN システムは 対応するゴールデンテスト(期待出力との比較テスト)の追加を要求する SHALL。
